## Behaviour summary (the contract the docs state)
- **Roles/viewers:** built-ins `player` (subject required), `render` (optional), `dealer`/`auditor` (forbidden, privileged); custom roles only from `def.roles`. `validateViewer` order: role known, subject rule, subject is a roster seat, privileged registered (`UNKNOWN_ROLE`, `SUBJECT_NOT_ALLOWED`, `UNKNOWN_SUBJECT`, `VIEW_DENIED`). A privileged role is registered iff some zone/template/counter `visibility` has an own key equal to it; `default` never registers or entitles it.
- **Audiences:** `public`, `hidden`, `owner` (owner is the viewer's seat, its team or its player), `team` (needs a team; a teamless seat has no teammates); `owner`/`team` need a subject; undeclared (`{}`) = hidden for everyone. Grants only add (never for `dealer`/`auditor`/subject-less viewers).
- **View:** sections in `VIEW_SECTION_ORDER`; statically entitled zone carries `count`, `members`, `orderKnown: true`; grant-only zones may lack `count` and have `orderKnown: false`; counters are decimal strings; derived counter with own visibility is governed by it, with none inherits `zone_count` of its zone. Faces: owner/team zone always, public zone only face-up, or grant; metadata `public`/`subject` (needs subject seat)/`secret` (registered privileged only)/undeclared never.
- **Delta:** entries by action index `i`; `zoneCounts` and `counters` always present; other sections only when changed; entitlements use the union of pre/post grants; `projectLogEntry` is the same function; `wouldReveal` returns `once` grants of `pre` whose removal changes some grantee seat's delta (each tested alone), `[]` for a mismatched batch.
- **Package v1:** field order `formatVersion, sessionId, definition{id,gameId,contentHash}, actionSchemaVersion, initial, params, log[{seq,eventId,principal,actions}], receipts[{principal,eventId,receipt}], digests[{seq,digest}], forkedFrom?`; idMaps travel as sorted `[key, value]` arrays; amounts are decimal strings; `decodePackage` tolerant of whitespace/key order, strict on content, max 100 errors, default 64 MiB.
- **Replay:** `rebuild` order binding (`definition.id`, `gameId`, `contentHash`, `actionSchemaVersion`: `REPLAY_MISMATCH`), `uptoSeq` range, initial state (seq 0, active, digest equals a fresh session from the initial roster; a seat without a player is valid), fold (non-empty, gapless, logged primitives only, `apply` with no proposal, unbound reducer = `REPLAY_INVALID`), recorded digests up to `uptoSeq`. Accepts decoded package, `Uint8Array` or `{raw}` (the last two go through `upgradeToCurrent` when not current). `advance` = one step. `forkFromSeq` takes a decoded package, verifies by rebuilding, re-keys `initial.id`, `receipts: []`, `forkedFrom`.
- **Version policy:** versions stay replayable; chain append-only; `assertUpgraderChain` is `null` for the real constants (`{1}`, `PACKAGE_UPGRADERS = []`). Checklist to add version N+1 is in `docs/replay-package.md` ("Adding a schema version and an upgrader").

## Known gaps (documented in the docs as limits)
- Grant selectors are card, zone, top-of-ordered-zone only. `control`, `roster`, `outcome` have no visibility declarations (public to every non-denied viewer).
- Deltas carry no grant-derived content (added grant, re-resolved `top`, ended `until_seq`); a `move` entry has no orientation; a card that transits a visible zone mid-batch is named even if it ends hidden; a zone-level `card_face` grant can attach a face to a `move` entry whose id came from the source zone.
- `buildPackage` keeps its own fold and does not run upgraders; `decodePackage` does not check id charsets and accepts any integer `actionSchemaVersion` (only `rebuild` rejects); a decoded package cannot be upgraded (pass bytes/`{raw}`); `forkFromSeq` takes a decoded package.
- `readSealedBatch` is internal by convention only (the rule guards `open-batch`). Rebuild heap is measured as retained growth after forced GCs, not as a peak.
- Replay of YAML-compiled definitions needs reducer functions bound (Phase 4); until then only code-built fixtures replay `meta`/`roster` actions.
- Strict numbers were measured on a laptop; the Docker baseline-runner numbers are whatever the Docker run prints (thresholds are enforced there).
