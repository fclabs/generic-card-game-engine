# Game definitions

How a game becomes something the engine can run: the files an author writes, how they are validated and compiled, how a definition gets its content-addressed `DefinitionId`, how the hook bundle is built, how the filesystem registry loads and re-verifies definitions, why each of these works the way it does, and what it does not do yet.

Companion pages: [game-definition-schema.md](./game-definition-schema.md) (every `game.yaml` key and error code), [server-config.md](./server-config.md) (the operator's `server.yaml` and `pnpm config:check`), [canonical-json-profile.md](./canonical-json-profile.md) (the byte format identity is built on) and [domain-kernel.md](./domain-kernel.md) (what runs a compiled definition).

## Overview

A game is a directory:

```
games/<id>/
  game.yaml        declarative content: seats, zones, cards, counters, control, hooks, policies
  hooks.ts         optional: the functions game.yaml refers to by name
  dist/            generated by `pnpm bundle:games`, git-ignored
    hooks.js         one self-contained ES module
    hooks.manifest.json   {"exports": ["a", "b"]}
```

Four pieces turn it into a running definition:

| Piece | Where | What it does |
|-------|-------|--------------|
| `parseYaml` | `@cge/config` | Safe YAML to plain JSON data (no code, no tags, bounded size). |
| `compileDefinition` | `@cge/core` | Pure, synchronous: the parsed value to a `CompiledGameDefinition`, or every error with its path. No I/O, no clock, no randomness. |
| Identity functions | `@cge/core` | `definitionContentHash`, `hookBundleHash`, `computeDefinitionId`. |
| `buildHookBundle` and `createFilesystemDefinitionRegistry` | `@cge/config` | Build the bundle with esbuild; load every game under the search paths and resolve a `DefinitionId` back to its compiled definition. |

The split is deliberate: everything that touches files, the YAML library, the bundler or the environment lives in `packages/config`; the compiler and the hashes are pure so they can run anywhere the kernel runs. A malformed definition fails at load with the exact path and entity, not at the first move of a live game.

**Not in this phase.** Visibility semantics (compiling the declarations into who-sees-what: Phase 3), hook execution (running hooks, the time and cost limits on them and binding reducer functions to a compiled definition: Phase 4) and a registry service (remote bundles, hot reload, pinning: Phase 14) are later phases. The bundle is built, hashed and checked by name; it is never executed.

## Writing and checking a game

1. Create `games/<id>/game.yaml`. The directory name must equal the `id` in the file. The [worked example](./game-definition-schema.md#worked-example) is a complete game.
2. If the game references hooks or reducers, write `games/<id>/hooks.ts` exporting each referenced name and set `hooks.module: ./hooks.ts`.
3. Build the bundle and check everything:

```sh
pnpm bundle:games
ENGINE_HOST_KEY=0123456789abcdef pnpm config:check --games games
```

`pnpm bundle:games` prints one line per game (`bundle:games: built mini-tricks (7 exports, <bundle hash>)`) and exits 1, naming every failing game, if any bundle fails to build. `pnpm config:check --games games` loads the sample server config and then every game exactly as the server will, printing `OK <n> definitions` or one `<path>: <code>: <detail>` line per error. See [server-config.md](./server-config.md#checking-a-configuration-pnpm-configcheck) for flags and exit codes.

A minimal `hooks.ts` for the worked example only has to export the seven names it uses; the signatures are defined when hooks start executing:

```ts
export const validatePlay = () => ({ ok: true });
export const onTrickComplete = () => [];
export const setup = () => [];
export const resolvePass = () => [];
export const authorize = () => ({ allow: true });
export const reduceScore = (partition: unknown) => partition;
export const reduceRoster = (roster: unknown) => roster;
```

Hook code may import helper files from inside the game directory (they are inlined), but not Node built-ins or npm packages: the bundle targets a neutral platform with nothing to resolve them against.

## Identity: from a directory to a `DefinitionId`

Replay packages bind to a `DefinitionId`, so the id must cover **everything replay depends on** and nothing else. Three values are involved.

```
contentHash = sha256( canonical( definitionIdentitySchema, definitionData(definition) ) )
bundleHash  = sha256( canonical( bundleIdentitySchema, { js: sha256(hooks.js bytes), exports: [sorted, distinct names] } ) )
DefinitionId = "sha256:" + sha256( canonical( idIdentitySchema, { contentHash, bundleHash? } ) )      // 71 characters
```

`canonical(...)` is the frozen canonical JSON profile ([canonical-json-profile.md](./canonical-json-profile.md#definition-identity)). All hashes are lower-case hex SHA-256.

### What `contentHash` covers

The compiled definition's data: `gameId`, roles, schema version, every card (in order, with type, metadata schema, initial metadata and metadata visibility), zones and templates (with owner and visibility), counters (bounds, scale, rounding, supply role, owner, visibility and the derived-counter spec), conservation groups, seats and teams, view keys, control, meta schemas (reducer **names** and field visibility), the roster reducer **name**, policies and the hook binding table. No function is part of it: derived-counter evaluators and bound reducers are not data, and the identity data carries only their declarations (`derivedSpec`, `reducerRef`, `rosterReducerRef`).

### Ordering rules

- **Sequences keep their order**: cards, seats, teams, zones, counters, turn order, hook lists. The order of cards is the initial order of every zone, so it changes the game. Swapping two generator axes changes the card order and therefore the hash.
- **Keyed collections are sorted**: id-keyed maps (visibility rules, metadata schemas, the hook binding table) are written in sorted order by UTF-16 code unit, so the order they were written in the YAML is irrelevant.
- **Generator order comes from the axis list**, never from mapping-key order: the first axis varies slowest.
- Field order inside each record is fixed by the schema. The schema's order is frozen: reordering a field would change every id.

### What changes the id, and what does not

| Changes the id | Does not change the id |
|----------------|------------------------|
| Any semantic field: a card's zone or position, a counter bound, a seat's team, a visibility audience, a policy value, the order of a hook list, `gameId`, a view key, a metadata value, a field's visibility, the number of seats a `for_each` expands over | Comments, whitespace, YAML key order, anchors and aliases |
| One byte of `hooks.js`, or an added, removed or renamed export | An explicit value equal to its default (`enforce_active_seats: false`, `phases: [main]` with `initial_phase: main`) |
| Having a bundle at all: a game with an empty bundle and a game with no bundle never share an id | `hooks.module` itself (a build input, not data) |
| A different `esbuild` version that emits different bytes (see [bundle build](#the-hook-bundle-build)) | The directory a game lives in, or where it was built |
| | `dist/` content beside a game that references no hooks (it is ignored) |
| | Binding reducer functions to the definition later |

`definitionNeedsBundle(raw)` decides whether a game has a bundle: true when `hooks.module` is set or any reducer or hook is referenced. A game that does not need one is identified without it (`computeDefinitionId(contentHash)`), even if a stale `dist/` sits next to it.

## The hook bundle build

`buildHookBundle(gameDir)` (and `pnpm bundle:games` over every `games/*/`) turns `hooks.ts` into `dist/hooks.js` and `dist/hooks.manifest.json`. It uses a pinned `esbuild` with fixed options so that the same sources always give the same bytes, wherever they are built:

- one self-contained ES module (all local imports inlined), `platform: neutral`, target ES2022, no minification, no source map, no legal comments, UTF-8 output;
- the only comments in the output are the source file names **relative to the game directory**, so no absolute path or timestamp is embedded;
- the build ignores any `tsconfig.json` above the game, so the repository's own settings cannot change the output;
- the manifest is `{"exports": [...]}`, sorted and distinct, plus one trailing newline. Only the export list (not the manifest file itself) enters the bundle hash.

Failures are `BUNDLE_INVALID`: `hooks.module` missing or malformed, a missing file, a build error (each message with `file:line:column`, at most 10), or a module with no exports while the YAML references hooks. A module without exports is fine when nothing references it. Nothing is written when the build fails.

The bundle is never executed, in the build, in the compiler or in the registry. A static test scans the non-test sources of `packages/core/src/definition` and `packages/config/src` for dynamic import, `require`, `eval`, `new Function` and `vm`.

## The registry

`createFilesystemDefinitionRegistry({searchPaths, limits})` loads **every** game directory of every search path once, at start-up, and returns `{registry, definitions}`: a `DefinitionRegistry` (the port declared in `@cge/core`) and a summary (`definitionId`, `gameId`, `schemaVersion`) per game.

**Loading.** Search paths are scanned in the order given, game directories in name order. Hidden entries (`.gitkeep`), files and dot-directories are ignored; symbolic links to directories are followed; an empty search path is fine and yields zero definitions. For each directory: read `game.yaml` (`GAME_YAML_MISSING`), parse it, check the directory name equals `id` (`GAME_ID_MISMATCH`), then only if the game needs a bundle read `dist/hooks.js` and `dist/hooks.manifest.json`, hash them, compile with the configured `limits` and compute the id. A search path that is not a directory is `SEARCH_PATH_MISSING`; a game `id` declared in two directories is `DUPLICATE_ID`. One invalid game fails the whole load, and the result lists **all** errors of all games, each with its `path` prefixed by the game directory (`<searchPath>/<dir>/<original path>`, or just the directory for a root error).

**Resolving.** `resolve(id)` returns `Result<CompiledGameDefinition, RegistryError>` and never throws:

| Outcome | When |
|---------|------|
| the compiled definition | the game's files still produce exactly this id (a comment-only edit still does) |
| `UNKNOWN_DEFINITION` | the registry never produced this id |
| `DEFINITION_HASH_MISMATCH` | the files changed so that they now produce another id; the detail names the expected and actual ids |
| `DEFINITION_INVALID` | the game no longer compiles, or its directory or bundle files are gone |

A file edited after load can therefore never yield a different definition under an old id. For speed, `resolve` keeps the bytes read at load time and returns the cached definition when they are unchanged; any difference triggers a full reload and id comparison. The registry is built once: it does not watch files, hot-reload or discover games added later.

**Limits.** The `limits` option carries the server's engine ceilings (`definitionLimitsFromConfig(config)`): a game may lower `cascade_cap` and the cost budgets but not exceed them.

**Reusing the contract.** `packages/config/src/registry-contract.testing.ts` is an adapter-agnostic test suite (resolve, unknown id, hash mismatch after a semantic edit and after a one-byte bundle edit, comment-only edit still resolving, broken source). It takes a factory, imports only `vitest` and `@cge/core`, and is meant to be reused by any other adapter.

## YAML safety

A definition is untrusted text. `parseYaml` enforces: YAML 1.2 core schema (so `yes` and `no` are strings), at most 1 MiB and 100 aliases, duplicate keys rejected (also through aliases), no tags, no merge keys (`<<`), no non-string keys, no `__proto__`, exactly one non-empty document, finite numbers only. Alias expansion is bounded a second time because 100 aliases can still nest into an exponential document; a "billion laughs" document fails in milliseconds. It never throws, and never reads files, the network or the environment. YAML errors carry the line and column in the `detail` text.

## Why it works this way

Decisions that bind anyone reading or extending this code.

**Identity**

- *The identity schema is part of the identity, and its field order is frozen.* Fields added by this phase are appended at the end of each record in the order they were introduced, rather than placed where they read best, because the schema extends the original one and a reorder would change every committed hash. The expected hashes of two committed fixtures (a full definition and the performance-floor definition) are stored next to the tests; they change only on purpose, in the same commit as the change that caused it.
- *Functions never enter identity.* The identity data has no "has a reducer" flag. If it did, binding the reducer functions later would change the id of an unchanged game. The compiled definition carries `reducerRef` and `derivedSpec` instead, and the bundle hash covers the code those names refer to.
- *`hookBundleHash` sorts and de-duplicates the export names itself.* Hashing must be total, and any caller (the build, the registry) then gets the same value however it listed them.
- *`bundleHash` is left out of the id data when there is no bundle*, so "no bundle" and "empty bundle" are different ids.
- *A new `esbuild` version is a schema-level change.* Bundle bytes are produced by that exact version (it and `yaml` and `zod` are pinned to exact versions); an upgrade that changes the output changes every id that has a bundle.

**Compilation**

- *Errors are collected, with paths, and `ok` implies the identity can be computed.* A compiled definition has already been canonicalised and has passed the kernel's structural assertion before `ok` is returned, so `definitionContentHash` never throws for it. Those last checks are a safety net: errors of this kind are reported against the compiled path (`cards[3].initialMetadata.x`), not the YAML path, because generators make the mapping back lossy.
- *Dependent sections are skipped, not cascaded.* Failed seats mean zones, counters and groups are not checked, and failed roles skip role-name checks, rather than reporting hundreds of "unknown reference" errors that disappear once the first problem is fixed.
- *Generated-id faults are reported once per generator.* A generator producing 10 000 cards with the same bad pattern reports its first offender and stops.
- *Metadata is type-checked once per generator, statically.* A placeholder that is exactly one token is checked against the axis's value kinds; mixed text is a string. This costs one check instead of one per card and never reports the same fault 10 000 times. Nested `json` values are never substituted.
- *The ceiling constrains declared values, not the default.* An absent `cascade_cap` is 16 without a ceiling check; clamping it to the ceiling would make a game's identity depend on the server's settings. A declared value above the ceiling is `LIMIT_EXCEEDED`. The ceiling is the server's `limits.cascade_cap.max`; the game's own range is 1 to 256.
- *Built-in role names are `DUPLICATE_ID`, not `RESERVED_NAME`.* `RESERVED_NAME` means exactly the `engine.` schema-id prefix.
- *`MISSING_HOOK_MODULE` applies to any reference* (reducer or hook): a hook cannot resolve without a module. It is reported once, at the first reference; the bundle checks come last.
- *Hook and reducer names are JavaScript identifiers* (`default` works, `a-b` does not), because they are looked up as exports.
- *`initialMetadata` is checked by the kernel too.* A card's initial metadata must match its declared schema, mirroring the rule `set_metadata` enforces (declared field, then type). The compiler reports a path-bearing error first; the kernel's structural check is the backstop.
- *Unbound reducers are an engine fault, an undeclared schema is a caller fault.* `meta` for a declared schema without a bound function is `REDUCER_ERROR` ("reducer not bound: ..."); an undeclared `schema_id` stays `MALFORMED_ACTION`. The same split applies to roster reducers: `REDUCER_ERROR` when `roster_reducer` is declared but not bound, `MALFORMED_ACTION` when none was declared.

**YAML**

- *Two layers of alias protection.* Counting alias nodes (the 101st fails) is not enough on its own, and the library's expansion guard alone would let 101 flat aliases through; both are used. Documents that nest aliases beyond a weight of 10 000 fail even under 100 references.
- *Positions are in the `detail` text.* `DefinitionError` has a path, a detail and an entity; line and column are appended as ` (line L, column C)` rather than adding fields.
- *`<<` is rejected even when quoted.* Merge is off, so the key would otherwise silently become a plain key named `<<`.

**Bundles and the registry**

- *Absolute paths never reach the output.* The build runs relative to the game directory and writes the bytes itself, which is also what makes copying a game elsewhere yield the same bytes and hash.
- *Missing bundle files are `BUNDLE_MISSING` and a malformed manifest is `BUNDLE_INVALID`*, so an author who forgot `pnpm bundle:games` gets a path-bearing error per game, aggregated with the other games' errors. The registry never re-runs the build: it would write files, and loading must have no side effects.
- *The builder checks only "no exports while hooks are referenced".* Whether each referenced name is exported is the compiler's job (`UNKNOWN_HOOK_EXPORT`), where the reference paths are known. A module with no exports is valid when nothing references it.
- *`bundle:games` continues past a failure and reports every failing game*, so one run shows all work to do. With no `games/` directory it prints a message and exits 0.
- *The registry caches bytes, not mtimes.* Timestamps are unreliable; byte comparison is exact and the files are small.
- *Search-path and game errors are prefixed in `path`, not in `detail`*, keeping the error shape uniform and letting tools print `<path>: <code>: <detail>` directly.

**Server configuration**

- *Provenance decides redaction, not value matching.* Interpolation records which values came from the environment and the loader redacts those by path. Comparing error text against environment values would miss short or partial matches and could leak by omission.
- *Placeholders have no escapes and no defaults.* One templating rule keeps the redaction logic and the secret rule ("exactly one `${NAME}`") unambiguous.
- *`cascade_cap.default` is checked against `max` explicitly, not by narrowing its range.* This way a bad pair names both paths. The schema accepts 1 to 4096 and the cross-field rules enforce `<= max` and `<= 256`.
- *Every failure carries the loader's own expectation text.* `zod`'s default messages are never shown, so a library upgrade cannot change error text or leak a value.
- *`config:check` exits 2 for a bad command line.* Exit 1 would be indistinguishable from "the configuration is invalid".
- *Only the CLI entry reads `process.env`*, so the loader and the checker's logic stay testable with an injected environment.
- *Only the files the registry needs ship.* The Docker build stage runs `pnpm bundle:games` and copies only `game.yaml` and `dist/` of each game into `/app/games`; hook sources never reach the runtime image, and `/app/games` exists (empty) when there are no games, so the sample configuration validates.

## Limitations

- **Visibility is declared, not applied.** `visibility`, field visibility, `roles` and `view_keys` are validated, stored and part of the identity, and nothing yet changes what a participant receives (Phase 3).
- **Hooks and reducers are never run.** The manifest lists what the bundle should export; nothing yet checks that the module's actual exports equal it. Binding reducer functions onto the compiled definition and verifying them is Phase 4. Until then actions that need a reducer fail with `REDUCER_ERROR`.
- **No type checking of hooks.** esbuild strips types, so a type error in `hooks.ts` is not reported by `pnpm bundle:games`, and `pnpm typecheck` does not cover `games/` yet.
- **Hook code cannot import Node built-ins or npm packages.** Only files inside the game directory resolve. A violation is `BUNDLE_INVALID`.
- **The registry is built once** and never reloaded; adding a game needs a restart. It is a filesystem adapter, not a service: remote bundles, pinning and hot reload are later work (Phase 14), and so is moving the registry contract suite out of `packages/config`.
- **`loadServerConfig` only returns errors.** Turning them into a process exit is the server's job (Phase 7); `pnpm config:check` is the pre-flight check until then.
- **Derived counters** support only the size of a fixed zone.
- **No YAML positions for compile errors.** Compile errors carry a document path (`zones[2].id`) but no line and column; YAML syntax errors carry both.
- **At most 100 errors** per compile, in document order. Fixing early errors can reveal later ones (dependent sections are skipped).
- **Large integers need quoting.** An unquoted integer beyond 2^53 - 1 is already damaged by YAML parsing; it is rejected rather than rounded.
- **Rejected on purpose:** schema versions other than 1, floats anywhere inside `json` values, unknown keys at any level.

## Troubleshooting

| Symptom | Cause and fix |
|---------|---------------|
| `BUNDLE_MISSING` for a game (path `hooks.module` or the first reference) | `dist/` was not built: run `pnpm bundle:games`. In Docker the build stage does this; a host `dist/` is never copied in. |
| `UNKNOWN_HOOK_EXPORT` naming an export | `game.yaml` refers to a name `hooks.ts` does not export (or the bundle is stale after an edit: rebuild). |
| `MISSING_HOOK_MODULE` | A reducer or hook is referenced but `hooks.module` is not set. |
| `BUNDLE_INVALID` mentioning a package or `node:` import | Hook code imported a Node built-in or an npm package. Inline the code or import a file from the game directory. |
| `BUNDLE_INVALID`: module has no exports | `hooks.ts` is empty or exports nothing while `game.yaml` references hooks. |
| `DEFINITION_HASH_MISMATCH` from `resolve` | `game.yaml` or the bundle changed after the registry loaded. Restart (rebuild the registry) to pick up the new id. |
| `DEFINITION_INVALID` from `resolve` | The game no longer compiles or its files were removed after load; the detail lists the first errors. |
| `GAME_ID_MISMATCH` | The directory name and `id` differ. |
| `GAME_YAML_MISSING` for an empty directory | Any non-hidden directory in a search path must be a game. Remove it or start its name with a dot. |
| Same YAML, different `DefinitionId` on two machines | Different bundle bytes: check that both use the same `esbuild` version (`pnpm install --frozen-lockfile`) and the same sources. |
| Fewer errors than expected | Dependent sections are skipped after an earlier failure (for example everything after invalid `seats`). Fix and re-run. |
| `INVALID_VALUE` "write it as a quoted decimal string" | An integer beyond 2^53 - 1 was written bare; quote it. |
